# 만든 방식

저장소 작성자가 방향과 수용 기준(완성으로 인정할 조건)을 정했고, 코딩 에이전트(Claude Code)가 조사, 설계, 구현, 실험, 문서 초안을 실행했다. 이 사실은 커밋 메시지 끝의 트레일러에 적혀 있다.

## 주제를 고른 과정

1. 앞서 만든 저장소 두 개는 주제가 흔하거나 면접관이 보기에 설명이 복잡하다는 평가를 받았다
2. 같은 공고에 지원할 사람들의 프로젝트와 국내 개발자들의 공개 프로젝트를 조사한 뒤, 차별점이 분명한 주제로 다시 만들기로 했다([조사](research.md))
3. 조사에서 비어 있던 곳은 고장 정의, 작업지시와 민원의 결합, 운영과 검증이었다. 이 셋을 한 흐름으로 묶어 고장을 어떻게 정의하느냐가 모형을 바꾸는지를 정답이 있는 합성 로그에서 재는 주제로 정했다

## 판단과 실수

- 시뮬레이터를 처음 만들었을 때는 정답 라벨로 학습한 모형의 AUC가 0.58이었다. 정의 사이를 비교하기에 신호가 너무 적었다. 전조 기록을 넣고 위험의 가파름을 올려 모형이 배울 수 있게 했다. 조정 기준은 정답 라벨 모형과 손상 오라클의 AUC였다
- 고객별 정의 선택이 이득을 보이도록 시뮬레이터를 고치지 않았다. 사이트별 선택은 전 사이트 d2를 넘지 못했고, 그대로 적었다
- 정의를 고르는 지표를 F1로 만들었다가, 라벨 지표와 모형 성능의 상관을 재 보고 F1이 반대로 움직이는 것을 알아 F2로 바꾸었다. F2의 근거도 약하다는 것을 함께 적었다
- d6가 d2와 완전히 같게 나온 것을 발견해 정의를 바꾸었다
- 습관 변화 감시의 첫 버전이 거짓 경보를 많이 냈다. 분산 하한과 경보 기준을 조정했다. 조정 후에도 탐지는 20건 중 11건이다
- 전조 신호가 d2의 우위를 만든 것은 아닌지 의심해 전조를 0까지 줄인 세계에서 다시 돌렸다
- API 테스트가 필요한 열이 빠진 CSV에서 500이 나는 오류를 잡았다

## AI 사용 공개

코드와 문서의 초안은 에이전트가 썼다. 사람이 하지 않으면 아무도 검토하지 않았을 부분은 테스트와 CI로 고정했다.

- 미래 기록을 잘라도 특징이 같은지 확인한다(`tests/test_models.py`)
- 현장 확인 추정값이 정답의 평균과 맞는지 확인한다(`tests/test_eval.py`)
- 확인표를 만들고 추정하는 흐름이 정답과 맞는지, CLI 끝에서 끝까지 확인한다(`tests/test_audit.py`)
- 정의 엔진이 손으로 만든 작은 로그에서 기대한 사건 수를 내는지 확인한다(`tests/test_define.py`)
- 문서의 숫자가 산출물과 일치하는지 확인한다(`scripts/fill_numbers.py --check`, CI)
- README가 말하는 결론(d2가 d1보다 높음, 사이트별 선택이 d2를 못 넘음 등)이 산출물에서 여전히 참인지 확인한다(`tests/test_artifacts.py`)
- 커밋된 정적 데모가 산출물에서 만든 것과 같은지, 콘솔의 모든 탭이 오류 없이 열리는지 CI에서 확인한다

## 다시 돌려 보기

```bash
make install && make pipeline     # 시뮬레이션, 실험, 정적 데모, 문서 숫자 (4 vCPU 기준 약 10분)
make test
make serve                        # http://localhost:8000/console/
```
