# 틀리는 경우와 한계

## 결과가 뒤집히거나 사라지는 경우

| 경우 | 확인한 내용 |
|---|---|
| 사이트 습관이 모두 같다 | 정의 사이의 AUC 차이가 <!-- num:summary.auc.spread|.3f -->0.061<!-- /num -->에서 <!-- num:summary.auc.spread_uniform|.3f -->0.025<!-- /num -->로 줄고, 최선이 d3 계열로 바뀐다. 이 프로젝트의 주장은 사이트 사이에 입력 습관이 다를 때만 의미가 크다 |
| 사이트마다 최선의 정의가 갈리지 않는다 | 확인 80건으로 사이트별 정의를 골라도 AUC <!-- num:summary.customization.audit_80|.3f -->0.632<!-- /num -->로 전 사이트 d2(<!-- num:summary.customization.fixed_d2|.3f -->0.638<!-- /num -->)보다 낫지 않다. 사이트별로 정의를 달리하는 것이 이득이라는 증거는 얻지 못했다 |
| 정의를 F1로 고른다 | 라벨의 F1은 모형의 진짜 AUC와 반대로 움직인다(순위 상관 <!-- num:summary.validity.f1|.2f -->-0.39<!-- /num -->). 정밀한 라벨은 좋은 학습 라벨이 아니다 |
| 라벨이 늦게 채워진다 | 학습 라벨을 100주째 기록으로 만들어도, 충분히 기다린 라벨과 AUC 차이가 <!-- num:summary.maturity.mature_minus_current|.3f -->-0.001<!-- /num -->로 없다. 입력 지연을 걱정할 이유를 이 세계에서는 찾지 못했다 |

## 검증이 못 하는 것

- 현장 확인은 320건으로도 최선의 정의를 90% 이상 고르지 못한다. 확인 건수가 적으면 선택이 흔들린다(10건에서 최선과 0.02 이내인 비율 <!-- num:multiseed.base.audit.p_near.0|.0% -->31%<!-- /num -->). 건수에 따라 잃는 점수가 꾸준히 줄어드는 것만 확인했다
- 현장 확인 결과가 틀릴 수 있다. 확인자가 4주 안의 고장을 잘못 기억하는 경우를 모형에 넣지 않았다
- 정의를 고르는 지표 F2의 근거도 약하다. 시드 5개 평균 상관이 <!-- num:summary.validity.f2|.2f -->0.39<!-- /num -->이고 시드마다 흔들린다. 재현율만으로는 항상 가장 넓은 정의를 고르게 되어 쓰지 않았다

## 감시가 놓치는 것

- 습관이 바뀐 <!-- num:summary.drift.shifts|d -->20<!-- /num -->곳 중 <!-- num:summary.drift.detected|d -->11<!-- /num -->곳만 탐지했다. 늦게 입력하던 사이트가 표준으로 바뀌는 경우는 5곳 중 <!-- num:summary.drift_by_target.standard.detected|d -->1<!-- /num -->곳, 입력 누락으로 바뀌는 경우는 5곳 중 <!-- num:summary.drift_by_target.missing.detected|d -->2<!-- /num -->곳만 잡았다
- 탐지까지 중앙값 <!-- num:summary.drift.delay_median_weeks|.0f -->32<!-- /num -->주가 걸린다. 그동안 d1의 F1은 이미 <!-- num:summary.drift.d1_f1_before|.2f -->0.66<!-- /num -->에서 <!-- num:summary.drift.d1_f1_after|.2f -->0.48<!-- /num -->로 내려가 있다
- 바뀌지 않은 사이트·실행 <!-- num:summary.drift.quiet_site_runs|d -->140<!-- /num -->건 중 <!-- num:summary.drift.false_alarm_site_runs|d -->3<!-- /num -->건에서 거짓 경보가 났다. 경보 기준을 낮추면 놓침은 줄지만 거짓 경보가 빠르게 늘었다(조정 중에 확인)
- 습관이 서서히 변하는 경우는 시험하지 않았다. 변화는 한 주에 계단처럼 일어난다고 가정했다

## 시뮬레이터에 기대는 부분

- 사이트 습관 6가지와 파라미터는 사람이 정했다. 실제 사이트의 습관이 이 정도로 갈리는지는 모른다
- 손상이 클수록 경미 작업과 약한 민원이 늘어난다는 전조를 넣었다. 전조를 0까지 줄여도 d2가 d1보다 높게 나오지만, 모형이 배울 신호가 줄어서 모든 숫자가 달라진다([평가](evaluation.md))
- 모형이 배울 신호의 크기를 맞추려고 시뮬레이터를 조정한 적이 있다([시뮬레이터](simulator.md)). 정의 순위를 목표로 하지 않았지만, 조정하는 동안 정의 비교를 같이 돌려 보았다
- 사이트 안에서 설비끼리 영향을 주고받는 고장이 없다
- 센서 값이 없다. 센서가 있는 현장에서는 라벨 문제가 달라진다

## 구현의 한계

- 코드표 제안(`suggest_code_book`)은 빈도 순서로 예방, 시정, 긴급을 짐작하는 거친 규칙이다. 제안일 뿐이고 사람이 확인해야 한다
- 민원 군집이 설비 하나로 특정되지 않으면 사건을 만들지 않는다. d3와 d4의 재현율이 낮아지는 쪽으로 틀린다
- 민원 증상은 내장 목록(냉방불량, 소음 등 12가지)만 읽는다. 실제 민원 문장을 증상으로 바꾸는 부분은 없다
- 콘솔은 인증과 요청 한도가 없는 데모다. 업로드는 행 수만 제한한다

## 만들면서 바로잡은 것

- d6를 처음에 사건 시각만 바꾼 d2로 만들었더니 d2와 완전히 같았다. 작업지시만 증거일 때는 가장 이른 증거와 입력일이 같기 때문이다. d3의 시각만 바꾼 정의로 다시 만들었다
- 정의 선택 지표를 처음에 F1로 만들었다. 라벨 지표와 모형 성능의 상관을 재 보고 F1이 반대로 움직이는 것을 알아서 F2로 바꾸었다
- 습관 변화 감시는 처음에 경보 기준을 5로 두고 분산에 하한이 없었다. 시드 3개에서 바뀌지 않은 사이트·실행 84건 중 26건에서 경보가 났다. 건수가 적은 구간의 분산에 하한(한 건)을 두고 기준을 10으로 올린 뒤에는 140건 중 3건이다
- 필요한 열이 빠진 CSV를 올리면 422 대신 500이 나던 오류를 API 테스트가 잡았다
