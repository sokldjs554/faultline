# 설계

## 문제

시설관리 소프트웨어의 작업지시 로그로 고장 예측 모형을 만들려면 먼저 고장 라벨이 있어야 한다. 로그에는 고장이라는 열이 없다. 있는 것은 작업지시(유형, 설비, 생성일), 민원(층, 증상, 날짜), 점검 기록이다. 어떤 기록을 고장으로 칠지는 사람이 정한다.

- 긴급으로 입력된 작업지시만 고장으로 본다
- 예방이 아닌 작업지시를 모두 고장으로 본다
- 긴급이거나 같은 증상의 민원이 받쳐 주는 작업지시만 고장으로 본다

사이트마다 입력 습관이 다르면 같은 정의가 사이트마다 다른 사건을 만든다. 긴급 코드를 거의 쓰지 않는 사이트에서는 첫 번째 정의가 고장을 거의 못 잡고, 경미한 작업까지 긴급으로 입력하는 사이트에서는 오탐이 많다. 이 차이가 모형에 얼마나 전달되는지는 정답이 있어야 잴 수 있다.

## 주장

> 고장 정의는 모형이 배우는 정답을 바꾼다. 정의를 파일로 쓰고, 정답을 아는 로그에서 라벨과 모형을 진짜 고장과 비교하면, 정의가 틀렸을 때 겉보기 성능이 어떻게 속이는지 볼 수 있다.

## 구성

```
시뮬레이터 ──> 로그(작업지시, 민원, 점검)   진짜 고장(정답, 모형은 보지 못함)
                    │                            │
        유형 정규화·품질 점검                     │
                    │                            │
   정의 파일(YAML) ──> 정의 엔진 ──> 사건 ──> 라벨 품질(정답과 매칭)
                                       │
                                       └─> 설비·주 라벨 ──> 모형(HGB, MLP) ──> 점검 순서
                                                                │
                                           진짜 고장으로 채점 <──┘
현장 확인 표본 ──> 정의별 정밀도·재현율 추정 ──> 정의 선택
작업지시 로그 ──> 습관 신호 ──> CUSUM ──> 현장 확인을 다시 하라는 경보
```

## 평가 프로토콜

| 항목 | 값 |
|---|---|
| 예측 단위 | 설비 x 주. 그 주를 마친 시점에서 다음 4주 안에 고장이 있는가 |
| 특징 | 그 시점까지 입력된 기록만 사용(점검, 작업지시, 민원, 사이트 수준 습관). 미래 기록을 잘라도 같은 값인지 테스트로 확인 |
| 학습 | 주 26~95의 행. 라벨은 100주째 직전까지 입력된 기록으로 만든 것 |
| 평가 | 주 104~151의 행. 진짜 고장(정답)과 정의가 만든 라벨(겉보기) 두 가지로 채점 |
| 점검 인력 | 사이트·주마다 점수 상위 5개 설비 |
| 지표 | AUC, 점검 100번당 적중, 사이트 안에서만 비교한 AUC |
| 모형 | HistGradientBoosting, 같은 입력의 PyTorch MLP(설비 종류 임베딩) |
| 시드 | 기본 5개(7, 11, 23, 31, 47), 대조 세계 3개 |

학습 라벨을 100주째 시점의 기록으로 만드는 이유는 늦게 입력되는 작업지시가 아직 로그에 없는 상태를 재현하기 위해서다. 평가는 104주째부터 시작해 학습 라벨이 쓴 기록과 겹치지 않는다.

## 선택과 이유

- 시뮬레이터를 쓴다. 정의를 채점하려면 진짜 고장이 필요한데 실제 로그에는 없다
- 모형은 하나로 고정하고 라벨만 바꾼다. 차이가 라벨 정의에서 오는지 모형에서 오는지 가르기 위해서다
- 특징은 정의와 무관하게 같다. 정의별로 특징을 따로 만들면 비교가 흐려진다
- 정의는 코드가 아니라 파일이다. 고객사 담당자가 읽고 고칠 수 있고 버전을 붙인다
- 현장 확인은 설비·주 단위로 한다. 사건 단위로 확인하면 정의가 만든 사건만 보게 되어 놓친 고장을 셀 수 없다
- 정의를 고르는 기준은 F2(재현율을 정밀도보다 두 배 무겁게 봄)다. F1이 모형 성능과 반대로 움직이는 것을 [평가](evaluation.md)에서 확인했다. F2도 약한 근거이며 한계로 적었다
- 습관 변화 감시는 정답 없이 작업지시 로그만 쓴다. 운영 중에는 진짜 고장을 모르기 때문이다

## 이름

faultline은 고장(fault)을 가르는 선(line)을 뜻한다. 같은 로그에서 어디까지를 고장으로 보느냐가 이 프로젝트의 주제다.
